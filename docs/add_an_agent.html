BurnScope — adding a new agent

How to teach BurnScope about a new AI coding agent. The firmware contract is agent-agnostic, so this is entirely laptop-side work. For how the pieces fit together see architecture.html; for the byte-level contract see wire-format.md.

1. Where the work lives

There is no Agent base class to subclass. The firmware renders whatever AgentSnapshot it is handed and never learns which agent produced it, so everything agent-specific happens upstream of schema.AgentSnapshot on the laptop. Your job is to read your agent's usage data, shape it into an AgentSnapshot, and hand it to the shared push path. The five shared modules (§3) do the rest.

2. Pick a lifecycle

How you collect depends on how your agent exposes its usage. The two agents we ship are the two templates.

2.1 Statusline-style (per-fire)

Use this when the agent will run your code and hand you the data, on its own schedule. claude_statusline.py is a Claude Code statusline hook: Claude invokes it after each assistant message with a payload that already contains rate_limits.*. The foreground process renders the status line and forks a detached --push child that builds the snapshot and pushes it. Nothing stays resident.

2.2 Daemon-style (long-lived)

Use this when you have to hold a connection open to get the data. codex_daemon.py owns a codex app-server subprocess and polls account/rateLimits/read on a timer. A long-lived process lets you dedupe across polls (only push when usage actually changed) and reconnect with backoff. It is more code than the statusline path; reach for it only when a per-fire hook can't get at the data.

3. Shared modules to reuse

Compose these — don't reimplement them. They live in client/src/burnscope_client/.

ModuleWhat you call it for
schema.py The AgentSnapshot / SessionSnapshot frozen dataclasses you build. AgentSnapshot.semantically_equal() lets a daemon skip pushes when nothing changed.
identity.py Resolve the plaintext identifier you send in the X-BurnScope-Client-Id header. Add a resolver for your agent's account email if it isn't already covered.
discovery.py discover_all(timeout, agent=…) to find displays on the LAN over mDNS and filter to ones with a free slot for your agent.
host_cache.py Atomic per-agent state in ~/.burnscope/: the paired device list, last-push outcomes, and the mDNS-reconcile cooldown. Your agent gets its own files keyed by name.
pusher.py push_to_all() to fan out POST /summary to every paired device, plus the host-reconciliation helpers (refresh_and_retry_transport_failures, reconcile_duplicate_hosts) the shipped collectors run after each push.

4. Step by step

  1. Read your agent's usage data from its native, zero-cost source — a payload it hands you, a file it already writes, or a subprocess it exposes. No upstream API calls or header scraping.
  2. Map it into an AgentSnapshot (§5).
  3. Resolve the client identifier with identity.py.
  4. Load the paired device list from host_cache.py; on an empty first run, browse with discovery.py and pair (the TOFU claim fires on the first push).
  5. Push with pusher.push_to_all(), then run the same reconciliation chain the shipped collectors do (refresh_and_retry_transport_failures → reconcile_duplicate_hosts) and record the outcomes. Drop a device only on a /summary 401; transport and health failures never evict.
  6. Register a burnscope install <agent> path (§6).

5. Building the snapshot

An AgentSnapshot is the agent name, the capture time, and one or more SessionSnapshot windows. used_pct is a fraction in 0.0–1.0 (not a percentage). Set rolling=True and window_duration_mins for windows whose resets_at drifts with wall-clock, so the firmware can synthesise a fresh countdown when it goes idle. 

from burnscope_client.schema import AgentSnapshot, SessionSnapshot

snapshot = AgentSnapshot(
    agent="myagent",            # lowercase identifier, shown on screen
    captured_at=now_unix,       # Unix seconds (UTC), monotonic per device
    sessions=[
        SessionSnapshot(
            type="current",     # agent-defined label
            used_pct=0.42,      # 0.0–1.0
            resets_at=reset_unix,
            rolling=False,
            window_duration_mins=300,
        ),
    ],
)

The field names and rules match wire-format.md exactly — the C side parses the same JSON, so keep the two in step.

6. Wiring the installer

Add an install path to cli.py so burnscope install <agent> wires your collector into the right supervisor:

  • Statusline-style — patch the agent's config to call your hook, the way _install_claude() writes the statusline command into ~/.claude/settings.json.
  • Daemon-style — drop a supervisor unit, the way _install_codex() installs a launchd plist (macOS) or a systemd --user unit (Linux) that runs the daemon.

Add your agent to the install/uninstall choices and to the per-agent loops in status and pair-reset so the tooling reports and resets it alongside the others.
