BurnScope — architecture

How the pieces fit together: laptop-side collectors that read what your AI coding agents already write to disk, a small HTTP wire format, and ESP32 firmware that renders the numbers. For the byte-level contract see wire-format.md; to add support for a new agent see add_an_agent.html.

1. Overview & data flow

BurnScope has no server. A collector on your laptop reads the rate-limit data your agent already produces, finds the ESP32 on the local network over mDNS, and pushes the latest numbers straight to it over HTTP. The display holds the last push and renders it until the next one arrives. 

┌───────────────────────────────┐       POST /summary           ┌────────────────────┐
│  Per-agent collectors         │ ────────────────────────────▶ │  ESP32 display     │
│   - Claude statusline hook    │   AgentSnapshot JSON          │   - mDNS advert    │
│   - Codex app-server daemon   │   + X-BurnScope-Client-Id     │   - HTTP server    │
│  Shared: schema, discovery,   │                               │   - NVS pairing    │
│  identity, pusher, host_cache │                               │   - LVGL renderer  │
└───────────────────────────────┘                               └────────────────────┘

Nothing is scraped from an upstream API and no credentials leave the machine. Each collector reads a source the agent writes for its own use, shapes it into an AgentSnapshot, and sends it. One display can hold two agents at once (Claude and Codex) and cycles between them.

2. Client (laptop side)

The client lives under client/src/burnscope_client/. It is not a single daemon. The v1 design had one Agent abstract base class and a shared asyncio loop; v2 dropped that because the two agents we support have genuinely different shapes. Each collector now reads from an agent-native, zero-cost source on its own schedule. The full spec is client-spec-v2.html (the historical v1 spec is client-spec.html).

2.1 Shared modules

Everything an agent has in common with every other agent lives in five modules. A new collector composes these rather than subclassing anything.

ModuleResponsibility
schema.py SessionSnapshot and AgentSnapshot — frozen dataclasses that mirror wire-format.md. This is the boundary: everything agent-specific happens upstream of it.
discovery.py mDNS browse for _burnscope._tcp.local. discover_all(timeout, agent=None) returns every resolved device with per-agent pairing hints from the TXT records; pass agent=… to keep only devices whose slot is still free.
identity.py Resolves the plaintext identifier sent in the X-BurnScope-Client-Id header. For Claude it prefers oauthAccount.emailAddress from ~/.claude.json. No hashing — the device shows the value on screen.
host_cache.py Atomic file-backed state in ~/.burnscope/ — the paired device list, last-push outcomes, and the mDNS-reconcile cooldown map. See §2.3.
pusher.py POST /summary and GET /health. push_to_all() fans out to every paired device in parallel. A 401 (PushAuthError) is kept distinct from a transport error so callers know whether to drop the device or just record a failure.

2.2 Two collector lifecycles

The two agents we ship differ in how their usage data becomes available, so each has its own lifecycle. These are the two templates a new agent follows.

Statusline-style (per-fire)

claude_statusline.py is a Claude Code statusline hook. Claude runs it after each assistant message and hands it the runtime payload, which already carries rate_limits.*. The foreground process renders the status line and forks a detached --push child; the child builds the snapshot, fans out the push, runs host reconciliation, and exits. There is no long-running process.

Daemon-style (long-lived)

codex_daemon.py owns a codex app-server subprocess and runs reader, pusher, health, and poll coroutines. The poll loop calls account/rateLimits/read every 60 s and dedupes so that wall-clock drift in Codex's resetsAt does not trigger a push when usage hasn't actually changed. It reconnects with exponential backoff on EOF. See codex-app-server.html.

2.3 On-disk state

All client state is per-agent and lives in ~/.burnscope/ (override with BURNSCOPE_STATE_DIR). Pairing is trust-on-first-use: the first successful /summary push binds the device to the collector's identifier, recorded in paired-devices.<agent>.json. A device is only forgotten on a /summary 401 or an explicit burnscope pair-reset — transport failures and failed health checks never evict, so a display that is merely asleep or off-network is not dropped.

3. The wire-format seam

The daemon ↔ firmware contract is hand-mirrored in both Python (schema.py) and C (the firmware snapshot store), and is structurally agent-agnostic: any well-formed AgentSnapshot parses. The agent name is not free-form, though — the firmware validates it against a fixed allowlist (KNOWN_AGENTS), keeps one display slot per known agent, and picks a per-agent icon. So most of adding an agent is a laptop-side job, but a new name also needs a few firmware edits; both are covered in add_an_agent.html.

The full contract — request shapes, TOFU pairing, the monotonic captured_at rule, the /health response, error codes, and POST /ota — is in wire-format.md. In short: POST /summary carries the snapshot JSON plus the X-BurnScope-Client-Id header; the device binds that id on first push and answers 401 on a mismatch.

4. Firmware (ESP32 side)

The firmware lives under firmware/ and is built with ESP-IDF. Several display boards ship from the same source tree; one is selected at build time. The HTTP server, mDNS advertisement, snapshot store, and NVS pairing are shared across all of them — only the panel driver and the LVGL layout change per board.

4.1 Display profiles

A display profile bundles a panel driver with the UI layout that fits that panel, because layout is geometry-bound (a 320×240 rectangle and a 466×466 circle want different screens). Each profile lives in main/displays/<name>/ and is chosen by a Kconfig choice in main/Kconfig.projbuild. The target chip picks a sensible default profile via sdkconfig.defaults.<target>.

ProfileChipPanelKconfig symbol
cyd2usb_st7789ESP32ST7789 320×240 LCDCONFIG_BURNSCOPE_DISPLAY_CYD2USB_ST7789
amoled_sh8601ESP32-S3SH8601/CO5300 466×466 (1.43")CONFIG_BURNSCOPE_DISPLAY_AMOLED_SH8601
amoled_co5300_175ESP32-S3CO5300 466×466 (1.75")CONFIG_BURNSCOPE_DISPLAY_AMOLED_CO5300_175

The two AMOLED boards share the round-display UI and the QMI8658 IMU stack (auto-rotate and motion-wake). The 1.75" board adds a CST9217 touch controller and an AXP2101 PMU that the firmware reads (read-only) for the battery indicator. The CYD has none of these and uses a static rotation. See the matrix in the README for what each board implements, and firmware/README.md for the per-board build commands.

4.2 Partition layouts

Flash size drives the partition table, which differs by board.

BoardFlashTableLayout
CYD4 MBpartitions-4mb.csv Two ~1.875 MB OTA slots, no data partition.
AMOLED (1.43" / 1.75")16 MBpartitions-16mb.csv Two 5 MB OTA slots plus a ~5.8 MB storage partition, mounted as LittleFS at /storage by main/storage.c, reserved for the future pixel-aging map and persistent assets.

4.3 OTA & rollback

After the initial USB flash, updates ship over the LAN: burnscope ota <bin> --device <id> on the client and the POST /ota handler in main/http_server.c on the device. /ota writes the inactive slot and uses the same client-id slot match as /summary, but it never TOFU-binds — a device has to have been paired by a prior /summary push first.

On the ESP32-S3 boards the bootloader has rollback enabled (CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE): a freshly flashed image has to mark itself valid after its first healthy /summary push, and anything that boots but never proves itself is reverted on the next reboot. The CYD's 4 MB layout does not carry this safety net, so a bad image there needs a USB re-flash to recover.
