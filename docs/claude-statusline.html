Claude statusline — rate-limit procedure

1. Why statusline

The historical Claude probe (docs/probe-claude.sh) authenticates with the user's OAuth token and POSTs a near-empty request to https://api.anthropic.com/v1/messages, then reads anthropic-ratelimit-unified-{5h,7d}-{utilization,reset} from the response headers. That issues a real (token-costing) API call on the user's account and reuses an authentication channel intended for the official client — it works, but is on shaky ground vs. Anthropic's terms of use.

Claude Code ships a documented extension point, the statusline, designed for tools like ccstatusline, claude-powerline, and Tokemon to render live session telemetry in the user's terminal. The statusline command receives a JSON payload on stdin that already contains rate_limits.five_hour.* and rate_limits.seven_day.* — the exact data we need. No upstream API call is made, no tokens are consumed; the data is sourced from the most recent API response Claude Code itself observed during normal usage.

2. Prerequisites

  • Claude Code installed and signed into a Claude.ai account.
  • Active Pro or Max subscription. The rate_limits object is only populated for Claude.ai subscribers; API-key-only accounts will never see it.
  • At least one message exchanged in the current session — the rate_limits object appears only after the first API response.

3. Configure the hook

Add a statusLine field to ~/.claude/settings.json: 

{
  "statusLine": {
    "type": "command",
    "command": "~/.burnscope/claude-statusline.py",
    "padding": 0
  }
}
FieldValue
typeAlways "command" (the only supported kind).
commandAbsolute path or shell command. Runs in a subshell, so inline pipes/jq are fine.
paddingOptional. Horizontal padding (chars) added to the rendered line. 0 for compact.
refreshIntervalOptional. Re-runs the command every N seconds (minimum 1) in addition to event-driven fires. Useful for time-based displays; not needed for our use.
hideVimModeIndicatorOptional. Set true if the script renders vim.mode itself.

Changes are picked up at the next event tick — no Claude Code restart needed.

4. Hook protocol

4.1 When the hook fires

Event-driven, with 300ms debounce. Triggers:

  • After each new assistant message.
  • After /compact finishes.
  • When the permission mode changes.
  • When vim mode toggles.
  • On the refreshInterval timer (if configured).
If a new event triggers while your script is still running, the in-flight execution is cancelled. Scripts must be fast or do their heavy work in a detached background process.

4.2 stdin payload (JSON)

A single JSON object piped to the command's stdin. Fields are documented in section 5. Read with: 

#!/usr/bin/env python3
import json, sys
payload = json.load(sys.stdin)
five_hour = payload.get("rate_limits", {}).get("five_hour", {})
print(f"5h {five_hour.get('used_percentage', '—')}%")

4.3 stdout expectations

  • Each line printed becomes one row of the rendered statusline.
  • ANSI color escapes are honored (terminal must support them).
  • OSC 8 hyperlinks are honored.
  • stderr is discarded — log there if you need to.
  • Exit code is ignored.

5. Rate-limit fields

The two fields BurnScope cares about, both under payload.rate_limits:

FieldTypeDescription
five_hour.used_percentagefloat (0–100)% of the 5-hour rolling window consumed.
five_hour.resets_atint (unix sec)UTC unix seconds when the 5-hour window rolls over.
seven_day.used_percentagefloat (0–100)% of the 7-day rolling window consumed.
seven_day.resets_atint (unix sec)UTC unix seconds when the 7-day window rolls over.

Other useful fields the same payload contains (not consumed today, but listed for reference):

FieldNotes
model.id, model.display_nameCurrent model.
session_id, transcript_pathPer-session identifiers. Not stable across restarts.
cost.total_cost_usdClient-side cost estimate.
context_window.used_percentagePer-conversation context fill (separate from rate limits).
versionClaude Code version string.

There is no user-, account-, or organization-level identifier in the statusline payload. For that, read oauthAccount.emailAddress (or top-level userID as a fallback) from ~/.claude.json — see client-spec-v2.html § Identity & pairing.

7. Mapping to AgentSnapshot

Source→SessionSnapshot
rate_limits.five_hour → { type: "current", used_pct: used_percentage / 100, resets_at: resets_at }
rate_limits.seven_day → { type: "weekly", used_pct: used_percentage / 100, resets_at: resets_at }

The type labels ("current", "weekly") match what the previous header-based probe produced — see the header→session table at the bottom of wire-format.md. No firmware change required; the swap is source-side only.

Per client-spec-v2.html, the Claude collector lives in the user's ~/.claude/settings.json as a statusline command — not a long-running daemon. captured_at is stamped at the moment stdin is read; the snapshot is then posted to the ESP32 in a detached background process so the rendered statusline isn't blocked by network I/O.

8. Caveats

  • Cancellation. If a new event fires before your script finishes, the script is killed mid-execution. Always print the statusline first, then fork the ESP32 POST off into a detached background process. The main script must exit fast.
  • Rate-limit absence. The rate_limits object is missing entirely for the first message of a fresh session (before any API response) and for non-subscriber accounts. Treat None as "no data yet" — don't post a partial AgentSnapshot; just print the statusline with dashes where the percentages would be.
  • Idle behavior. The hook only fires while Claude Code is open. When you close Claude Code, no further pushes happen — the ESP32 will show the last successful snapshot indefinitely (per the wire format's per-agent in-memory store). Acceptable; the user isn't watching the display when they're not using Claude.
  • Multi-session concurrency. Running N parallel Claude Code windows means N statusline scripts fire on every update, all posting independently. The wire format's per-agent monotonic captured_at guard (see wire-format.md) ensures the freshest snapshot wins; older arrivals are 204-acked without state change.
  • Throttling. 300ms debounce on the Claude Code side means at most ~3 fires/sec under continuous activity. The ESP32 handles this fine; no client-side rate limiting is needed.
  • Format stability. The statusline JSON shape is documented and stable, but Anthropic may add fields. Always null-check; never crash on unknown keys.
