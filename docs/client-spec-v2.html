1. Overview & deltas from v1

v2 replaces the per-agent OAuth-token HTTP probe (which made real, token-costing API calls to extract rate-limit headers) with two agent-native, no-cost data sources:

  • Claude → Claude Code's statusline hook. The hook is a script that Claude Code invokes after every assistant message, passing the current session's rate_limits on stdin.
  • Codex → the codex app-server JSON-RPC subprocess. Actively polls account/rateLimits/read on a 60 s cadence and dedupes against the last successfully pushed snapshot; account/rateLimits/updated notifications are still handled if they fire, but the long-lived app-server doesn't observe rate-limit changes that originate in other codex CLI processes, so polling is the authoritative trigger.

Both sources are documented, stable, and intended for third-party integrations. Neither consumes upstream tokens. The collectors have asymmetric lifecycles, so v2 abandons the v1 Agent ABC + unified asyncio daemon-loop pattern.

Two collectors, N ESP32 displays. The collectors share nothing on disk — each manages its own per-agent paired-device list and its own last-push state. No IPC, no shared process state, no shared token, no shared cache file.

3. Identity & pairing

v2 adds per-agent TOFU (trust-on-first-use) pairing: each collector reads a stable, human-readable identifier from local state that the agent already maintains, sends it plaintext on every request, and the ESP32 binds the first one it sees per agent into NVS. No hashing — the value is also the on-screen owner label rendered by the device. The user does nothing.

Source identifiers

AgentFileFieldFallback
Claude ~/.claude.json oauthAccount.emailAddress userID (top-level, 64-char string)
Codex codex app-server: account/read account.email none — daemon raises and reconnects

No OS keyring access, so no Keychain prompts on macOS and no libsecret / Secret Service dependency on Linux. Both sources are written by the upstream agent during normal sign-in and read by us with a plain file/IPC read.

Value semantics

The identifier is a printable ASCII string ≤ 254 bytes (RFC 5321 mailbox cap). The collector does no normalization beyond stripping leading/trailing whitespace — what the upstream agent wrote is what the ESP32 receives and stores. No hashing means the ESP32 can render the value verbatim on the owner row of each agent's display panel.

Pairing semantics

  1. ESP32 reads nvs::client_id[agent] at boot.
  2. Incoming request includes X-BurnScope-Client-Id: <identifier>:
    • NVS empty for this agent → accept, persist the incoming identifier.
    • NVS matches → accept.
    • NVS mismatch → 401 Unauthorized.
  3. To re-pair (user changed Claude org, sold the ESP32, etc.): erase NVS via idf.py erase-flash, or via the hardware boot-button-hold path (Phase-2 polish).

3.1 Multi-device pairing (per-agent slots)

The client supports one user owning multiple ESP32 displays simultaneously, and tells different users which devices on the LAN are still up for grabs. Pairing remains per-agent slot, matching the firmware's existing NVS schema — no firmware NVS change. What's new is the client-side multi-device tracking and the mDNS visibility into per-agent claim state.

Slot independence

A device's claude slot and its codex slot are independent claims. Different users may end up holding different slots on the same physical display.

Worked example:

  • User A: claude_A@example.com + codex_A@example.com.
  • User B: claude_B@example.com only.
  • User A pairs his Claude to screen X and his Codex to screen Y. Screen X advertises paired_claude=1, paired_codex=0; screen Y advertises paired_claude=0, paired_codex=1.
  • User B's burnscope pair claims her Claude on screen Y (its claude slot is free); screen X is skipped (paired_claude=1). Afterward, screen Y's display shows claude_B@example.com and codex_A@example.com side by side on their respective rows.

mDNS visibility

The firmware advertises two TXT records — paired_claude and paired_codex — that mirror the NVS slot state (see §4.3). They are an advisory hint only: in practice every collector path browses discover_all() unfiltered and relies entirely on the firmware's HTTP response (204 claims, 401 rejects) as the authoritative answer. Pre-filtering to paired_<agent>=0 would wrongly exclude a device whose slot is already TOFU-bound to us and block recovery after a paired-devices.json wipe — so the agent= filter on discover_all exists but no caller currently uses it.

Client-side state model

Each collector maintains its own paired-device list in ~/.burnscope/paired-devices.<agent>.json. A device may legitimately appear in both lists (User A's normal case above). The Claude collector never reads or writes the Codex collector's file, and vice versa.

Failure modes

EventBehavior
Push to device returns 401 Silently drop from this agent's paired list (remove_paired_device(agent, device_id)). No log, no error surfaced to the user. The device may be re-claimed on the next burnscope pair if it returns to paired_<agent>=0. /summary 401 is the only signal that removes a pairing.
Push to device transport-fails Keep in list; record ok:false in last-push.<agent>.<device_id> and bump consecutive_failures (diagnostic-only). refresh_and_retry_transport_failures runs one throttled mDNS browse (per-(agent, device_id) cooldown, default 60 s, gated by claim_reconcile_slots) and, if the device shows up at a different host, commits the new host via update_paired_device_host and retries the push once. If still failing — or the cooldown blocks the browse — the device stays paired and the next cycle tries again.
GET /health transport-fails or returns invalid JSON Same recovery shape as the push side: codex's health loop batches the failed devices into one throttled mDNS browse and retries /health at any refreshed host. On continued failure it debounces before marking the device unhealthy — ok=false is persisted only after HEALTH_FAILURE_THRESHOLD (5) consecutive misses (~2.5 min of silence at the 30 s interval). A single miss is treated as noise: an idle ESP32 in WiFi modem-sleep sometimes answers slower than the 5 s timeout while still accepting /summary fine. The streak resets on any healthy probe or any successful /summary push (proof of contact). Never evicts — only /summary 401 removes a pairing.
GET /health returns 401 (our client_id matches no populated slot) The firmware's authorize_health accepts when our id equals any populated slot; a 401 means at least one slot is bound but none to us. Causes: only another agent's slot is populated and ours is empty; a slot is now bound to a different id (another laptop won the race, or it's someone else's display); or a stale cached host where a different display answers after a DHCP reassignment. (A full NVS wipe leaves no slot bound, so /health instead accepts the probe and the empty-slot drift is healed via the body, not a 401.) fetch_health returns the HEALTH_AUTH_REJECTED sentinel — distinct from None — and the daemon treats it as a re-bind candidate, not a reachability miss. _verify_rebind_hosts first confirms via mDNS that the host still maps to this device_id; only then does a targeted /summary re-push run — which TOFU-binds an empty slot (204) but 401-drops a slot owned by a different id. Marks ok=false immediately — definitive, so it bypasses the consecutive-miss debounce. The probe itself never evicts (issues #66 / #67).
/health.device_id doesn't match the requested paired record (firmware ≥ 0.5.x) The cached host points at a different physical device (DHCP reassignment, or aliased with another paired entry). Treat as a stale-host conflict — the response is not a successful probe. The device is marked ok=false immediately (definitive: a different display identified itself, so the cached host is unambiguously stale — bypasses the consecutive-miss debounce) and routed through the round-2 mDNS reconciliation path. Older firmware that omits device_id is backwards-compatible: absence is treated as a match, and the daemon falls back to local duplicate-host detection alone.
Two paired records share the same cached host Identity conflict: an HTTP success against the shared host can't tell which physical device replied. reconcile_duplicate_hosts runs one throttled mDNS browse (shares the cooldown with the transport path), refreshes any visible duplicate via update_paired_device_host, and returns the set of device_ids that still alias another paired entry. Caller writes ok:false for the still-conflicting ids — both stay paired (plan §3 forbids removal here), but neither is reported as healthy until the conflict is split.
New device appears on the LAN after first-run Run burnscope pair; one unfiltered mDNS browse merges every device not already in the agent's list (a brand-new display's slot is free) via add_paired_device. The TOFU claim itself fires on the next push (statusline fire or Codex notification), which 401-drops the device if it's owned by someone else / another laptop won the race.
Auto-pair-on-first-run race (two clients claiming the same free device simultaneously) NVS is serialized — first writer wins. The loser sees 401 on its first push and silently drops the device.
Previously-paired device disappears for many cycles, then returns Self-healing. The pairing stays in paired-devices.<agent>.json through any number of transport / health failures (the per-device failure counters advance so burnscope status can surface the degraded device, but eviction is gone). When the device returns to mDNS, the next eligible reconciliation cycle (cooldown ≥ 60 s by default) catches the new host via update_paired_device_host and the next push or health probe succeeds — no burnscope pair needed. Stale browses started before a concurrent /summary 401 / pair-reset cannot resurrect a forgotten pairing because the update-only primitive returns False when the device is no longer present.
Pairing concurrently removed (/summary 401 or pair-reset) while an mDNS reconciliation is in flight update_paired_device_host returns False; the retry is dropped and no resurrected entry is written back. burnscope pair-reset also clears the reconcile cooldown map so a fresh re-pair doesn't have to wait for timestamps referencing forgotten devices.

4. Wire-format additions

Three additions to wire-format.md, all backward-compatible:

4.1 X-BurnScope-Client-Id header

Plaintext per-agent identifier (see §3) — no hashing. Sent on POST /summary and GET /health. Value rules: printable ASCII, no control characters, ≤ 254 bytes. Server enforcement (Phase-2 firmware) is per-agent TOFU:

  • If NVS has no stored identifier for the incoming request's agent → accept, persist.
  • If NVS matches → accept.
  • If mismatch → 401 Unauthorized (no state change).
  • If header absent → accepted only if NVS is empty for that agent (legacy-client compatibility window). Once any TOFU-paired client has POSTed, header-less clients for that agent are rejected with 401.

4.2 Monotonic captured_at guard

Per-agent. Firmware tracks the highest captured_at seen per agent. On POST /summary:

  • captured_at >= stored → update stored snapshot, update stored captured_at, return 204.
  • captured_at < stored → return 204 without updating state. The push is acknowledged so clients don't retry, but the older snapshot is dropped.

Equal captured_at is treated as last-writer-wins. The data is essentially identical at one-second resolution.

Together, the two guards mean a multi-laptop, multi-session deployment always converges to the freshest snapshot from an authorized client per agent.

4.3 Per-agent mDNS TXT records

The firmware adds two TXT items to its _burnscope._tcp.local. service advertisement:

TXT keyValueSemantics
paired_claude0 or 11 iff the claude NVS pairing slot holds a non-empty identifier.
paired_codex0 or 11 iff the codex NVS pairing slot holds a non-empty identifier.

The firmware updates the relevant paired_<agent> item via mdns_service_txt_item_set whenever the slot transitions (TOFU claim flips 0 → 1; factory-reset flips back to 0). HTTP-level auth is unchanged — the TXT record is an advisory hint for client-side filtering, and the 204 / 401 HTTP response remains the authoritative answer.

PushResult (dataclass) — device_id: str, ok: bool, kind: Literal["ok","auth","transport"]. Returned by push_to_all, one per device.
PushError, PushAuthError (exceptions) — raised by the single-host push(). PushAuthError covers 401; PushError covers transport / other non-2xx.

All requests carry the plaintext X-BurnScope-Client-Id header. push_to_all dispatches per-device pushes in parallel via asyncio.gather(return_exceptions=True), catches the two exception classes internally, and returns one PushResult per device. The caller (per-agent collector) inspects the dict and decides per device: kind="auth" → drop from paired list; kind="transport" → keep, mark per-device failure; kind="ok" → record success — unless the device is in the set returned by reconcile_duplicate_hosts, in which case kind="ok" is treated as unverified (see below).

refresh_and_retry_transport_failures takes the result of push_to_all and heals stale cached IPs. For each entry with kind="transport" it consults host_cache.claim_reconcile_slots to gate the browse (per-(agent, device_id) cooldown, default 60 s), runs one discover_all, commits any refreshed host via host_cache.update_paired_device_host (returns False if the device was concurrently unpaired — the retry is dropped), and re-pushes once at the new host. Devices not seen on mDNS, visible at the same host, inside cooldown, or removed during the browse keep their original transport-failure result.

reconcile_duplicate_hosts detects shared host values in the cached paired list (an identity conflict — HTTP success against the shared host can't tell which physical device replied). It short-circuits if no duplicates exist; otherwise it shares the same per-(agent, device_id) cooldown with the transport path, runs one discover_all, refreshes any visible duplicate via update_paired_device_host, and returns the set of device_ids whose cached host still aliases another paired entry after the pass. Pairings are never removed by this helper.

codex_daemon.py new

client/src/burnscope_client/codex_daemon.py

Long-running async process. Owns one codex app-server subprocess for the lifetime of the daemon. Restarts the subprocess on unexpected EOF. Four coroutines:

  • Reader — reads JSONL from app-server stdout, demuxes responses by id and notifications by method. On account/rateLimits/updated: build AgentSnapshot, enqueue push. (Notifications fire only when the app-server's own in-process cache changes; the Poll coroutine below is the authoritative trigger for changes that originate elsewhere.)
  • Pusher — consumes the push queue, fans out POST /summary via push_to_all, then runs refresh_and_retry_transport_failures and reconcile_duplicate_hosts to heal stale IPs and surface identity conflicts. Writes per-device last-push.codex.<device_id> only — no aggregate write; compute_aggregate_ok derives the verdict from those files on read. Advances _last_pushed_snapshot when at least one device's PushResult.ok is True and that device isn't in the duplicate-host-unverified set (gates the Poll coroutine's dedupe — see below). On any device's success it clears both _push_failures and _health_failures for that id: a successful /summary is proof of contact, so it resets the health debounce streak too (otherwise a push that lands between /health timeouts wouldn't stop the threshold from tripping). Transport failures bump the diagnostic _push_failures counter but never evict — only /summary 401 may remove a pairing.
  • Health — periodic GET /health. For each successful body, verifies device_id matches the requested paired record (mismatch = stale-host / identity conflict → marked ok=false immediately and rerouted into the round-2 reconcile path). A 401 (HEALTH_AUTH_REJECTED) means our client_id matches no populated slot (another agent's slot is the only one bound, the slot is owned by a different id, or a stale host) → the device is a re-bind candidate: _verify_rebind_hosts confirms the host via mDNS, then a targeted /summary re-push TOFU-binds an empty slot or 401-drops one owned by a different id. Devices whose round-1 probe timed out are batched into one shared throttled mDNS browse (via claim_reconcile_slots) with a single /health retry at any refreshed host. Then runs reconcile_duplicate_hosts on the post-recovery paired list and marks aliased devices unverified. On body divergence vs _last_pushed_snapshot (the anchored value the firmware actually has), re-pushes only to the diverged (and verified-rebind) devices. Transport timeouts are debounced: _record_health_failure persists ok=false only after HEALTH_FAILURE_THRESHOLD (5) consecutive misses — so _health_failures is no longer diagnostic-only, it gates the unhealthy write (the streak resets on any healthy probe or successful push). Definitive failures (device_id mismatch, a 401 on the post-mDNS-move retry) bypass the debounce and mark ok=false at once. Never evicts on any health signal.
  • Poll — every POLL_INTERVAL_S (60 s), sends account/rateLimits/read to the app-server, builds an AgentSnapshot, and enqueues it only when AgentSnapshot.semantically_equal reports a real change against _last_pushed_snapshot. Required because the long-lived app-server doesn't observe rate-limit changes that originate in other codex CLI processes (no file watchers on ~/.codex/state_*.sqlite); the notification path alone would push exactly once at bootstrap and then go silent.

Bootstrap sequence: initialize → account/read (caches email as the plaintext client_id) → account/rateLimits/read (initial snapshot) → enter reader loop.

6. Claude per-fire lifecycle

Steps in order, executed every time Claude Code fires the statusline:

  1. Read stdin as JSON; locate rate_limits.five_hour and rate_limits.seven_day.
  2. Read indicator state via compute_aggregate_ok("claude") (derives from the per-device last-push.claude.* files): True → ✓, False → ✗, None (pending: nothing paired yet, or a device with no recorded outcome) → ….
  3. Render statusline to stdout: 5h X% · 7d Y% ✓. If rate_limits is absent (first-message-of-session or non-subscriber), substitute dashes. Flush stdout.
  4. If rate_limits is absent → exit. Nothing to push.
  5. Build AgentSnapshot with captured_at = int(time.time()).
  6. Spawn detached child: Popen([sys.executable, __file__, "--push"], stdin=PIPE, start_new_session=True). Write the snapshot JSON to its stdin, close stdin, exit.
  7. (Child) Resolve client_id from host_cache.read_client_id("claude"); on cache miss, call identity.claude_user_identifier() (reads ~/.claude.json) and persist via host_cache.write_client_id("claude", id).
  8. (Child) Resolve paired devices: devices = load_paired_devices("claude"). If the list is empty (first-run or post-pair-reset), run discover_all() unfiltered (no agent= filter — a device whose claude slot is already TOFU-bound to us returns 204 and must be recovered after a paired-devices.json wipe; devices owned by someone else 401 and are skipped below), attempt to claim each discovered device by POSTing the snapshot with our client_id, and add_paired_device("claude", device) on every 204. 401 and transport failures are silently skipped during this auto-pair phase (next fire retries).
  9. (Child) Fan-out push via push_to_all(snapshot, devices, client_id, client).
  10. (Child) Heal transport failures via refresh_and_retry_transport_failures(…): gated by the per-(agent, device_id) reconciliation cooldown (default 60 s), runs at most one mDNS browse and re-pushes any device whose IP changed at its refreshed host. If update_paired_device_host returns False (concurrent /summary 401 / pair-reset), the retry is dropped.
  11. (Child) Identity check via reconcile_duplicate_hosts(…) on the post-recovery paired list: collects device_ids whose cached host still aliases another paired entry. Same throttle as the transport path.
  12. (Child) Per-device accounting. For each PushResult:
    • device_id ∈ unverified (identity conflict unresolved) → bump_push_failures(…); aggregate ok=False. Pairing preserved (plan §3 forbids removal on identity ambiguity). This branch is evaluated first, ahead of kind="auth": a 401 from a device whose cached host still aliases another paired entry cannot be attributed to a single physical device, so it is suppressed here rather than evicting a (possibly wrong) pairing. It self-heals once reconcile_duplicate_hosts splits the records via mDNS and the 401 becomes attributable on a later fire.
    • kind="ok" → reset_push_failures(…) (clears the diagnostic counter, writes ok=True).
    • kind="auth" → silently drop via remove_paired_device("claude", device_id); no aggregate state change attributable to this device. (Only reached when the device's host is not aliased — see the unverified branch above.)
    • kind="transport" → keep in list; bump_push_failures(…) for visibility in burnscope status; aggregate ok=False. Transport / health failures never evict — only /summary 401 does.
  13. (Child) No aggregate write. The per-device files written in step 12 are the source of truth; the next fire's compute_aggregate_ok("claude") derives the indicator from them, so it can never disagree with per-device state. overall_ok is returned only as the process exit code. If the paired list is empty after step 7 (no devices on the LAN), the child exits non-zero and writes nothing — the derived verdict is None (pending), not a failure.

Steps 1–6 happen synchronously on the foreground statusline-rendering path and must complete in well under 300ms (Claude Code's debounce window). The actual work — discovery, POST — happens in the detached child, immune to Claude's cancellation-on-next-event behavior.

7. Codex per-event lifecycle

Bootstrap (once per daemon start)

  1. Spawn codex app-server, attach to its stdio.
  2. Send initialize; await response.
  3. Send account/read; cache client_id = account.email (plaintext) for the daemon lifetime and persist via host_cache.write_client_id("codex", email).
  4. Send account/rateLimits/read for the initial snapshot; enqueue a push.
  5. Start the reader, pusher, and health coroutines.

Steady state (reader loop)

  1. Read a JSONL line.
  2. If it has an id matching a pending request → resolve that request's future. (Includes responses to the Poll coroutine's account/rateLimits/read requests.)
  3. If it has a method:
    • account/rateLimits/updated → build AgentSnapshot, set captured_at = now, enqueue push. Rarely fires in practice (the app-server only emits when its own in-process cache changes); the Poll coroutine is the authoritative trigger.
    • Other methods → log at debug, ignore.

Steady state (poll loop)

  1. Sleep POLL_INTERVAL_S seconds (default 60).
  2. Skip if self._client_id is None (bootstrap hasn't finished yet).
  3. Send account/rateLimits/read; on CodexProtocolError log at debug and loop.
  4. Convert the response via _snapshot_from_rate_limits; None → loop. Each session is tagged rolling: true with the upstream's windowDurationMins on the wire so the firmware can synthesise a local countdown during idle.
  5. Anchor the fresh snapshot via _anchor_resets_at(fresh, _last_pushed_snapshot): for each session whose used_pct matches the last-pushed entry of the same type, rewrite its resets_at to the last-pushed value. Required because codex's backend reports resetsAt as roughly now + remaining, so it slides ~60 s per 60 s of wall-clock at low usage. Without anchoring the dedupe key changes every poll and we'd push (and wake the firmware out of burn-in idle) once per minute. The firmware-side synthesis compensates for the stale resets_at when used_pct ≤ 0.01.
  6. If the anchored snapshot semantically_equal to _last_pushed_snapshot → debug-log "rate limits unchanged; skipping push" and loop.
  7. Otherwise enqueue the (anchored) snapshot for the pusher.

Pusher coroutine

  1. Await a snapshot from the queue.
  2. devices = load_paired_devices("codex"). If empty, run discover_all() unfiltered (no agent= filter, so a device already bound to us is re-claimed after a wipe), attempt to claim each via POST /summary with the cached client_id, and add_paired_device("codex", device) on every 204. Silent skip on 401 / transport.
  3. results = await push_to_all(snapshot, devices, client_id, client).
  4. results = await refresh_and_retry_transport_failures(snapshot, devices, results, …).
  5. unverified = await reconcile_duplicate_hosts("codex", load_paired_devices("codex")).
  6. Per device, write last-push.codex.<device_id> with ok = result.ok and device_id ∉ unverified and update the in-memory counters:
    • device_id ∈ unverified → keep pairing, bump _push_failures; per-device ok=False.
    • kind="ok" and not unverified → clear both _push_failures and _health_failures for that id (a successful push is proof of contact, so it also resets the health debounce streak); any-success advances _last_pushed_snapshot.
    • kind="auth" → silently remove_paired_device("codex", device_id) and clear both counters for that device.
    • kind="transport" → keep pairing, bump _push_failures (diagnostic-only; never evicts).
  7. No aggregate write. The per-device files above are the single source of truth; compute_aggregate_ok("codex") derives the overall verdict on read (this is what fixed the writer-disagreement bug class of #73). An empty paired list (every device 401-dropped) derives to None (pending), not a failure.

Health coroutine (every HEALTH_INTERVAL_S = 30 s)

  1. Round 1 — initial probe. For each device in load_paired_devices("codex"), call fetch_health (sends the client_id header). It returns one of three things, each routed differently:
    • HEALTH_AUTH_REJECTED (401) → reachable, but our client_id matches no populated slot (only another agent's slot is bound, the slot is owned by a different id, or a different display answers at a stale host — a full NVS wipe would instead accept). Append to rebind_devices and write ok=false now so state is honest if there's nothing to re-push. Not a reachability miss — and not necessarily a re-bind: the targeted re-push 401-drops a slot owned by a different id.
    • None (transport / non-2xx / invalid JSON) → append to failed_devices for round-2 recovery. A transient timeout, to be debounced, not believed on the first miss.
    • a dict body → run identity verification: compare body["device_id"] (firmware ≥ 0.5.x) against the expected record. A mismatch means a different physical display answered at the cached host — write ok=false immediately (definitive stale host, bypasses the debounce) and append to failed_devices so mDNS relocates it. A match (or an older firmware that omits the field) → _mark_health_ok.
  2. _mark_health_ok. Clears the device's _health_failures streak, then clears a stale ok=false only when all three hold: a delivery baseline exists this run (_last_pushed_snapshot is not None — a reachable probe alone, e.g. just after a restart, proves only reachability, not that the firmware holds current data); the firmware is not diverged from the last-pushed snapshot; and _push_failures == 0 (no newer snapshot is currently failing to deliver to this device). A diverged device is appended to diverged_devices for the targeted re-push instead.
  3. Round 2 — batched mDNS recovery. If failed_devices is non-empty, call _reconcile_health_failures: claim slots via claim_reconcile_slots (shared with the push-side throttle), run one discover_all, commit any refreshed host via update_paired_device_host (update-only), and retry /health once at the new host. Outcomes:
    • retry body → _mark_health_ok (healed).
    • retry None (still timing out) → debounced via _record_health_failure: ok=false is persisted only after HEALTH_FAILURE_THRESHOLD (5) consecutive misses; below that the device keeps its prior state so a transient blip never flips the derived aggregate red.
    • retry HEALTH_AUTH_REJECTED → ok=false immediately (definitive, bypasses the debounce — slot unbound at the now-correct host).
    • inside cooldown, not seen on mDNS, or same host → _record_health_failure (debounced), no browse.
    • pairing removed by a concurrent 401 / pair-reset during the browse → skipped without resurrecting.
    In every case the pairing is preserved — only /summary 401 evicts.
  4. 401 re-bind verification. If rebind_devices is non-empty and a _last_pushed_snapshot exists, _verify_rebind_hosts confirms via mDNS that each 401 device's host still maps to its device_id before any re-bind — a 401 at a stale host can be a different display after a DHCP reassignment, and blind /summary would TOFU-bind the wrong device. Only mDNS-confirmed hosts are returned (shares the reconcile cooldown).
  5. Duplicate-host check. reconcile_duplicate_hosts("codex", load_paired_devices("codex")) runs against the post-recovery list. Devices still aliasing another paired entry get a per-device ok=false write so the derived aggregate stays honest until reconciliation splits them.
  6. No aggregate write. The per-device files written above (round-1 branches, _mark_health_ok, _record_health_failure, the duplicate-host loop, and the re-push below) are the single source of truth; compute_aggregate_ok derives the verdict on read.
  7. Targeted re-push. Re-push _last_pushed_snapshot to diverged_devices + verified_rebind only — never the whole fleet, so idle peers aren't woken. Divergence is measured against _last_pushed_snapshot (the anchored value the firmware actually received); comparing against the raw _last_snapshot would manufacture a spurious divergence every cycle, since poll-loop anchoring keeps _last_pushed_snapshot stable while _last_snapshot tracks the drifting wire value. The re-push goes through _push_to_devices, which writes the true per-device outcome and (for a verified re-bind) TOFU-binds the empty slot or 401-drops a slot now owned by a different id.

Subprocess failure

If the codex app-server stdout EOFs, the reader fails out. The daemon backs off (exponential, max 60 s) and restarts the subprocess, going through bootstrap again. Identity may change if the user re-authenticated in between — that's fine, the ESP32 will accept if it's the same email, reject if not.

10. Migration from v1

v1 → v2 is not an in-place upgrade — too many files are removed and the daemon's role changes shape. Operator steps:

  1. Stop the v1 daemon (whatever launchd / systemd / nohup arrangement is in place). Remove its job file.
  2. Update the client install (pip install -e ./client).
  3. Run burnscope install claude and burnscope install codex.
  4. (Firmware) Flash the v2 firmware build, which includes the client-id auth, the monotonic guard, and the per-agent mDNS TXT records. NVS will be empty on first boot, allowing TOFU pairing.
  5. Start a Claude Code session; the statusline fires and pairs the Claude slot. The Codex daemon (already loaded by launchd) pairs the Codex slot at its first push.

v2 → v2+multi-device upgrade

An older client deployment had a single-host ~/.burnscope/host file. On the first read after upgrade, migrate_legacy_host_file() deletes the file and writes a one-shot v1-upgrade-hint that burnscope status surfaces. No state is converted: each collector's first fire afterward hits the empty paired-list branch, runs discovery, and tries to re-claim every visible device via a normal POST /summary. Whether that re-claim succeeds depends on what the device's NVS slot already holds:

  • If the slot holds this laptop's plaintext identifier (a device paired by an already-plaintext client) → 204, auto-reclaimed silently, no operator action.
  • If the slot holds a v1-era hashed client_id → the v2 client's plaintext identifier won't match → 401, and the device is silently skipped. This is why the migration writes the recovery hint: the operator must factory-reset each such device (clear NVS) and re-run burnscope pair. The hint text spells this out so burnscope status can guide them.

No data is migrated. The wire format is backward-compatible at the payload level, so an old v1 firmware would still accept v2 client pushes (it just ignores the new header and the monotonic logic isn't enforced). A new v2 firmware will, however, reject v1 client pushes once paired — by design. Firmware older than the per-agent TXT update is treated by the v2 client as "leave alone" (both paired_<agent> default to True when the TXT records are absent), so legacy devices are not auto-claimed — the user must burnscope pair-reset the firmware (factory reset) to bring it into the multi-device pool.
