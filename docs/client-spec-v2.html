1. Overview & deltas from v1

v2 replaces the per-agent OAuth-token HTTP probe (which made real, token-costing API calls to extract rate-limit headers) with two agent-native, no-cost data sources:

  • Claude → Claude Code's statusline hook. The hook is a script that Claude Code invokes after every assistant message, passing the current session's rate_limits on stdin.
  • Codex → the codex app-server JSON-RPC subprocess. Listens for account/rateLimits/updated server notifications.

Both sources are documented, stable, and intended for third-party integrations. Neither consumes upstream tokens. The collectors have asymmetric lifecycles, so v2 abandons the v1 Agent ABC + unified asyncio daemon-loop pattern.

3. Identity & pairing

v2 adds per-agent TOFU (trust-on-first-use) pairing: each collector reads a stable, human-readable identifier from local state that the agent already maintains, sends it plaintext on every request, and the ESP32 binds the first one it sees per agent into NVS. No hashing — the value is also the on-screen owner label rendered by the device. The user does nothing.

Source identifiers

AgentFileFieldFallback
Claude ~/.claude.json oauthAccount.emailAddress userID (top-level, 64-char string)
Codex codex app-server: account/read account.email none — daemon raises and reconnects

No OS keyring access, so no Keychain prompts on macOS and no libsecret / Secret Service dependency on Linux. Both sources are written by the upstream agent during normal sign-in and read by us with a plain file/IPC read.

Value semantics

The identifier is a printable ASCII string ≤ 254 bytes (RFC 5321 mailbox cap). The collector does no normalization beyond stripping leading/trailing whitespace — what the upstream agent wrote is what the ESP32 receives and stores. No hashing means the ESP32 can render the value verbatim on the owner row of each agent's display panel.

Pairing semantics

  1. ESP32 reads nvs::client_id[agent] at boot.
  2. Incoming request includes X-BurnScope-Client-Id: <identifier>:
    • NVS empty for this agent → accept, persist the incoming identifier.
    • NVS matches → accept.
    • NVS mismatch → 401 Unauthorized.
  3. To re-pair (user changed Claude org, sold the ESP32, etc.): erase NVS via idf.py erase-flash, or via the hardware boot-button-hold path (Phase-2 polish).

Why this works for every scenario

ScenarioBehavior
Same user, two laptops, both ClaudeBoth read the same oauthAccount.emailAddress → identical → both accepted. ✓
Same user, two laptops, both CodexBoth read the same account.email → identical → both accepted. ✓
Same user, Claude on one laptop and Codex on anotherPer-agent slots claimed independently. ESP32 shows both. ✓
Two users on same LAN, each own ESP32Different emails → each ESP32 only accepts its owner. ✓
First-run race attackSame TOFU surface as bare TOFU. Mitigation: pair while ESP32 is on your bench before exposing to LAN.
PII on the LANThe identifier (your email) is transmitted plaintext over your local network. Accepted trade-off in exchange for a human-readable label on the display.

4. Wire-format additions

Two additions to wire-format.md, both backward-compatible:

4.1 X-BurnScope-Client-Id header

Plaintext per-agent identifier (see §3) — no hashing. Sent on POST /summary and GET /health. Value rules: printable ASCII, no control characters, ≤ 254 bytes. Server enforcement (Phase-2 firmware) is per-agent TOFU:

  • If NVS has no stored identifier for the incoming request's agent → accept, persist.
  • If NVS matches → accept.
  • If mismatch → 401 Unauthorized (no state change).
  • If header absent → accepted only if NVS is empty for that agent (legacy-client compatibility window). Once any TOFU-paired client has POSTed, header-less clients for that agent are rejected with 401.

4.2 Monotonic captured_at guard

Per-agent. Firmware tracks the highest captured_at seen per agent. On POST /summary:

  • captured_at >= stored → update stored snapshot, update stored captured_at, return 204.
  • captured_at < stored → return 204 without updating state. The push is acknowledged so clients don't retry, but the older snapshot is dropped.

Equal captured_at is treated as last-writer-wins. The data is essentially identical at one-second resolution.

Together, the two guards mean a multi-laptop, multi-session deployment always converges to the freshest snapshot from an authorized client per agent.

schema.py

SessionSnapshot(type, used_pct, resets_at) and AgentSnapshot(agent, captured_at, sessions, to_dict()). Wire format is unchanged.

identity.py new

client/src/burnscope_client/identity.py

Pure module. Reads ~/.claude.json only.

SymbolSignatureDescription
claude_user_identifier () → str Returns Claude's plaintext identifier. Resolution: oauthAccount.emailAddress from ~/.claude.json; falls back to top-level userID when emailAddress is missing or empty. Raises IdentityError when both are absent or the file is missing/malformed.

No hashing function. The identifier travels plaintext on the wire so the ESP32 can render it (see §3).

The Codex equivalent (extracting email from account/read) lives in codex_daemon.py rather than here, because it requires an open app-server connection — pulling it into identity.py would introduce an awkward subprocess dependency in an otherwise pure module.

host_cache.py new

client/src/burnscope_client/host_cache.py

Manages the three files in the user's state directory. The state directory is ~/.burnscope/ on both macOS and Linux (no XDG branching — explicit and predictable across platforms; tools like ssh, aws, and gh use the same dot-directory pattern). Atomic writes via tempfile.NamedTemporaryFile + os.replace so concurrent statusline fires from multiple Claude sessions can't corrupt any file. Directory is created lazily on first write with mode 0700.

pusher.py

preserved from v1; extended with client-id header

Both functions add X-BurnScope-Client-Id: <hash> to the outgoing request. 401 responses raise PushError with a recognizable subclass so callers can decide whether to invalidate the host cache (transport failure) or surface a "not paired" error (auth failure — host is right, identity is wrong).

claude_statusline.py new

client/src/burnscope_client/claude_statusline.py

Module-level entry-point script invoked by Claude Code on every statusline fire. Two roles via argparse:

  • Default (no args) — read JSON from stdin, print statusline to stdout (including the indicator from read_push_state("claude")), fork a detached background child to do the push.
  • --push — read AgentSnapshot JSON from stdin (piped by the detached parent), run mDNS-cached POST /summary, call write_push_state("claude", ok=…).

See §6 for the full per-fire sequence.

codex_daemon.py new

client/src/burnscope_client/codex_daemon.py

Long-running async process. Owns one codex app-server subprocess for the lifetime of the daemon. Restarts the subprocess on unexpected EOF. Three coroutines:

  • Reader — reads JSONL from app-server stdout, demuxes responses by id and notifications by method. On account/rateLimits/updated: build AgentSnapshot, enqueue push.
  • Pusher — consumes the push queue, runs mDNS-cached POST /summary. After each attempt, calls write_push_state("codex", ok=…) so burnscope status can report health. On transport failure, invalidates the host cache and retries on the next event (no aggressive retry loop).
  • Health — periodic GET /health; on transport failure invalidates the host cache; on body mismatch with the latest snapshot, re-enqueues a push. Preserves v1's edge-triggered reconciliation guarantee for Codex.

Bootstrap sequence: initialize → account/read (caches email as the plaintext client_id) → account/rateLimits/read (initial snapshot) → enter reader loop.

cli.py

rewritten: installer/status, not a daemon entry point

v1's cli.py built an asyncio daemon. v2's is small and imperative — subcommands for one-shot operations:

CommandAction
burnscope install claude Patches ~/.claude/settings.json to add the statusLine entry pointing at claude_statusline.py. Idempotent.
burnscope install codex OS-detected service registration:
  • macOS → writes a launchd plist at ~/Library/LaunchAgents/com.burnscope.codex.plist and loads it with launchctl bootstrap.
  • Linux → writes a systemd user unit at ~/.config/systemd/user/burnscope-codex.service and enables it with systemctl --user enable --now.
Both arrange the daemon to start on user login and restart on crash. Fallback (no launchd / no systemd-user): print the command and ask the user to wire it up themselves.
burnscope uninstall {claude,codex} Reverses the above.
burnscope status Prints: cached ESP32 host, last push state per agent (from the state files), whether the Codex launchd job is loaded, whether the Claude statusline hook is configured. Useful for debugging.
burnscope pair-reset Removes the host cache so the next push rediscovers. Does not touch the ESP32 NVS — that's a firmware-side reset.

6. Claude per-fire lifecycle

Steps in order, executed every time Claude Code fires the statusline:

  1. Read stdin as JSON; locate rate_limits.five_hour and rate_limits.seven_day.
  2. Read indicator state via read_push_state("claude") (reads ~/.burnscope/last-push.claude): {"ok": true} → ✓, {"ok": false} → ✗, absent → ….
  3. Render statusline to stdout: 5h X% · 7d Y% ✓. If rate_limits is absent (first-message-of-session or non-subscriber), substitute dashes. Flush stdout.
  4. If rate_limits is absent → exit. Nothing to push.
  5. Build AgentSnapshot with captured_at = int(time.time()).
  6. Spawn detached child: Popen([sys.executable, __file__, "--push"], stdin=PIPE, start_new_session=True). Write the snapshot JSON to its stdin, close stdin, exit.
  7. (Child) Resolve host via host_cache.load(); on cache miss run mDNS, host_cache.store() the result.
  8. (Child) Resolve client_id from host_cache.read_client_id("claude"); on cache miss, call identity.claude_user_identifier() (reads ~/.claude.json) and persist via host_cache.write_client_id("claude", id). The value goes plaintext into the X-BurnScope-Client-Id header.
  9. (Child) POST /summary with the header. On success: write_push_state("claude", ok=True). On transport failure: invalidate_host() then write_push_state("claude", ok=False). On 401: write_push_state("claude", ok=False) but do not invalidate the host cache (the device is reachable; identity is the issue).

Steps 1–6 happen synchronously on the foreground statusline-rendering path and must complete in well under 300ms (Claude Code's debounce window). The actual work — discovery, POST — happens in the detached child, immune to Claude's cancellation-on-next-event behavior.

7. Codex per-event lifecycle

Bootstrap (once per daemon start)

  1. Spawn codex app-server, attach to its stdio.
  2. Send initialize; await response.
  3. Send account/read; cache client_id = account.email (plaintext) for the daemon lifetime and persist via host_cache.write_client_id("codex", email).
  4. Send account/rateLimits/read for the initial snapshot; enqueue a push.
  5. Start the reader, pusher, and health coroutines.

Steady state (reader loop)

  1. Read a JSONL line.
  2. If it has an id matching a pending request → resolve that request's future.
  3. If it has a method:
    • account/rateLimits/updated → build AgentSnapshot, set captured_at = now, enqueue push.
    • Other methods → log at debug, ignore.

Pusher coroutine

  1. Await a snapshot from the queue.
  2. host = load_host(); on miss, discover and store_host().
  3. POST /summary with the cached client_id header.
  4. On success: write_push_state("codex", ok=True).
  5. On transport failure: invalidate_host(), write_push_state("codex", ok=False).
  6. On 401: write_push_state("codex", ok=False); do not invalidate the host cache.

Health coroutine (every 30 s)

  1. GET /health with the client_id header.
  2. On transport failure: invalidate_host().
  3. On success: compare body's per-agent sessions against the last pushed snapshot. On divergence (firmware lost state), enqueue the latest snapshot for re-push.

Subprocess failure

If the codex app-server stdout EOFs, the reader fails out. The daemon backs off (exponential, max 60 s) and restarts the subprocess, going through bootstrap again. Identity may change if the user re-authenticated in between — that's fine, the ESP32 will accept if it's the same email, reject if not.

8. Installation

# one-time, per laptop (macOS or Linux)
pip install -e ./client
burnscope install claude   # patches ~/.claude/settings.json (OS-agnostic)
burnscope install codex    # macOS → launchd plist; Linux → systemd user unit
burnscope status           # confirm wiring

No credential setup at install time. No token to copy. No flashing the ESP32 with a secret. First push pairs the ESP32 to the laptop's identifier (Claude's account email or userID; Codex's account email); subsequent pushes from the same account on any laptop are accepted because each collector reads the same field from the same upstream source.

10. Migration from v1

v1 → v2 is not an in-place upgrade — too many files are removed and the daemon's role changes shape. Operator steps:

  1. Stop the v1 daemon (whatever launchd / systemd / nohup arrangement is in place). Remove its job file.
  2. Update the client install (pip install -e ./client).
  3. Run burnscope install claude and burnscope install codex.
  4. (Firmware) Flash the v2 firmware build, which includes the client-id auth and the monotonic guard. NVS will be empty on first boot, allowing TOFU pairing.
  5. Start a Claude Code session; the statusline fires and pairs the Claude slot. The Codex daemon (already loaded by launchd) pairs the Codex slot at its first push.

No data is migrated. The wire format is backward-compatible at the payload level, so an old v1 firmware would still accept v2 client pushes (it just ignores the new header and the monotonic logic isn't enforced). A new v2 firmware will, however, reject v1 client pushes once paired — by design.
