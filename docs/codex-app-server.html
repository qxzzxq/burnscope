Codex app-server — rate-limit procedure

1. Why app-server

The historical Codex probe (docs/probe-codex.sh) authenticates with the user's OAuth token and POSTs a near-empty request to https://chatgpt.com/backend-api/codex/responses, then reads x-codex-{primary,secondary}-{used-percent,reset-at} from the response headers. That issues a real (token-costing) API call on the user's account and reuses an authentication channel intended for the official client — it works, but is on shaky ground vs. OpenAI's terms of use.

Codex CLI v0.124+ ships a documented subprocess, codex app-server, that exposes a JSON-RPC 2.0 surface for first-party integrations (CodexMonitor, CodexBar, the official VS Code extension, etc.). Its account/rateLimits/read method returns the same primary/secondary window data we want, sourced from the locally cached state the CLI already maintains. No upstream API call is made, no tokens are consumed, and the integration surface is sanctioned.

2. Prerequisites

  • Codex CLI installed: codex --version reports at least codex-cli 0.124.0 (any 0.130+ is verified).
  • The CLI is signed in to a ChatGPT account (~/.codex/auth.json exists). The app-server uses the same auth blob; no extra setup needed.
  • No network connectivity required to OpenAI for the rate-limit read itself — the data comes from the local cache populated by prior CLI activity.

3. Quick try

Pipe two JSON-RPC lines into codex app-server and read the responses: 

{ printf '%s\n%s\n' \
  '{"id":1,"method":"initialize","params":{"clientInfo":{"name":"burnscope","version":"0.0.1"}}}' \
  '{"id":2,"method":"account/rateLimits/read","params":{}}'; sleep 1; } \
  | codex app-server | head -3

The first line on stdout is the initialize response, the second is usually an unsolicited notification (e.g. remoteControl/status/changed), and the third is the rate-limits result. A real client demultiplexes by matching the id field, not by line position.

The trailing sleep 1 is load-bearing: without it, printf closes its stdout the instant it finishes writing, the server sees EOF on stdin, and shuts down before it has a chance to flush the response to request 2. You'll see lines 1 and 2 but the rate-limits reply gets lost. The head -3 is only there to let the pipeline exit cleanly once enough data has arrived. In production code, keep stdin open for the lifetime of the subprocess and demux responses asynchronously — see /tmp/codex-probe.py for a reference read-loop.

4. Protocol

4.1 Transport & framing

WireJSONL — one JSON object per line on stdin/stdout
EncodingUTF-8
DialectJSON-RPC 2.0, with the "jsonrpc":"2.0" envelope field omitted
DirectionBidirectional. Server may emit notifications at any time, interleaved with responses to your requests.
Start commandcodex app-server (defaults to --listen stdio://)
Alternative transports--listen unix://PATH, --listen ws://IP:PORT

Every line on stdout is either a response (has an id matching one of your requests) or a notification (has a method but no id). A read loop must check both.

4.2 Initialize handshake

The first request on a fresh connection must be initialize. The server replies with platform metadata and starts emitting state-change notifications.

Request

{
  "id": 1,
  "method": "initialize",
  "params": {
    "clientInfo": { "name": "burnscope", "version": "0.0.1" },
    "capabilities": {
      "experimentalApi": false,
      "optOutNotificationMethods": []
    }
  }
}
FieldRequiredDescription
clientInfo.nameyesIdentifier embedded in User-Agent.
clientInfo.versionyesClient version string.
capabilities.experimentalApinoOpt into experimental methods. We don't need this for rate limits.
capabilities.optOutNotificationMethodsnoNotification methods to suppress, e.g. ["thread/started"] to silence per-turn chatter we don't care about.

Response

{
  "id": 1,
  "result": {
    "userAgent": "burnscope/0.130.0 (Mac OS 26.3.1; arm64) ...",
    "codexHome": "/Users/you/.codex",
    "platformFamily": "unix",
    "platformOs": "macos"
  }
}

4.3 account/rateLimits/read

stable One-shot query for the current rate-limit snapshot. Use this immediately after initialize for the seed value, then rely on notifications for live updates.

Request

{ "id": 2, "method": "account/rateLimits/read", "params": {} }

Response shape

The result has two views of the same data: rateLimits (backward-compatible single-bucket) and rateLimitsByLimitId (multi-bucket, keyed by metered limit_id). For the codex CLI plan, both contain the same entry. We read the top-level rateLimits for simplicity. 

{
  "id": 2,
  "result": {
    "rateLimits": <RateLimitSnapshot>,
    "rateLimitsByLimitId": {
      "codex": <RateLimitSnapshot>
    }
  }
}

RateLimitSnapshot

FieldTypeDescription
limitIdstring | nullMetering key, e.g. "codex".
limitNamestring | nullHuman label. Usually null for the default codex bucket.
primaryRateLimitWindow | nullThe shorter rolling window (5h for ChatGPT Plus/Pro).
secondaryRateLimitWindow | nullThe longer rolling window (7d for ChatGPT Plus/Pro).
creditsCreditsSnapshot | nullPay-as-you-go credit balance. Out of scope for MVP.
planTypeenum string | null"free", "plus", "pro", "business", …
rateLimitReachedTypeenum string | nullNon-null when a limit is exhausted.

RateLimitWindow

FieldTypeDescription
usedPercentinteger (0–100)Percentage of the window consumed. Required.
windowDurationMinsint64 | nullWindow length. ChatGPT Plus today: 300 (5h) for primary, 10080 (7d) for secondary.
resetsAtint64 | nullUnix seconds (UTC) when the window rolls over.

4.4 account/rateLimits/updated

stable server → client Server-initiated notification, emitted whenever the cached rate-limit state changes. Sit on this and you get event-driven updates with no polling. 

{
  "method": "account/rateLimits/updated",
  "params": {
    "rateLimits": <RateLimitSnapshot>
  }
}

Same RateLimitSnapshot shape as section 4.3. No id field — this is a notification, not a response. Do not reply.

5. Sample response (annotated)

Captured live against codex-cli 0.130.0 with a ChatGPT Plus account that had just sent a few prompts: 

{
  "rateLimits": {
    "limitId": "codex",
    "limitName": null,
    "primary":   { "usedPercent":  1, "windowDurationMins":   300, "resetsAt": 1779261506 },
    "secondary": { "usedPercent":  0, "windowDurationMins": 10080, "resetsAt": 1779848306 },
    "credits":   { "hasCredits": false, "unlimited": false, "balance": "0" },
    "planType":  "plus",
    "rateLimitReachedType": null
  },
  "rateLimitsByLimitId": {
    "codex": { ... same as above ... }
  }
}

Decoding:

  • primary: 1% used of the 5-hour window (300 min), rolls over at 1779261506.
  • secondary: 0% used of the weekly window (10080 min = 7 d), rolls over at 1779848306.
  • planType: "plus" — useful for UI labels, not consumed by the MVP firmware.

6. Mapping to AgentSnapshot

The Codex agent collector converts each non-null RateLimitWindow into one SessionSnapshot entry (wire-format.md):

Source→SessionSnapshot
rateLimits.primary → { type: "primary", used_pct: usedPercent / 100, resets_at: resetsAt }
rateLimits.secondary → { type: "secondary", used_pct: usedPercent / 100, resets_at: resetsAt }

This is the same wire-format vocabulary the previous header-based probe produced (see the header→session table at the bottom of wire-format.md). No firmware change is required — the swap is source-side only.

If windowDurationMins is null or resetsAt is null for a window, skip that window (do not emit a partial SessionSnapshot). If both primary and secondary are null the snapshot has an empty sessions array — the daemon treats it as "no data yet" and withholds the push.

7. Generating schemas locally

The exact wire shape on your installed CLI version can be dumped without reading source: 

codex app-server generate-json-schema --out /tmp/codex-schema
ls /tmp/codex-schema/v2/ | grep -i ratelimit

The relevant files in v2/:

FilePurpose
GetAccountRateLimitsResponse.jsonResponse schema for account/rateLimits/read.
AccountRateLimitsUpdatedNotification.jsonPayload schema for the account/rateLimits/updated notification.
codex_app_server_protocol.v2.schemas.jsonCombined schema bundle — every type, every method name.

Method names are extractable from the combined bundle with: 

grep -oE '"[A-Za-z]+(/[A-Za-z]+)+Method"' \
  /tmp/codex-schema/codex_app_server_protocol.v2.schemas.json \
  | sort -u

Wire-side method strings are the lowercased prefix — e.g. the schema title Account/rateLimits/readRequestMethod corresponds to the on-wire method: "account/rateLimits/read".

8. Caveats

  • Subprocess lifetime. The app-server is long-lived. The collector should spawn it once at daemon start and keep it alive — not spawn-per-probe. Restart on unexpected EOF.
  • Notification interleaving. Notifications can arrive between your initialize request and its response, or between any request and its response. The read loop must demux by id, not assume "next line is my reply."
  • Overload back-pressure. Under load the server responds with JSON-RPC error code -32001 ("Server overloaded; retry later."). Retry with exponential backoff and jitter; do not hammer.
  • No upstream authentication state means no data. If ~/.codex/auth.json is missing or expired, the server starts fine but account/rateLimits/read returns an error result. The collector treats this the same as the old probe's CredentialsError — log and back off; do not crash.
  • Versioning. The v2 namespace is the current stable surface. The protocol is designed for backward compatibility, so older clients keep working against newer servers — but pin codex-cli >= 0.124 as a soft minimum and parse only fields documented above.
  • Plan dependence. The 5h + 7d window pair is what ChatGPT Plus/Pro plans expose. free and enterprise plans can return different shapes (e.g. primary only, or credit-only buckets). Always null-check both windows.
