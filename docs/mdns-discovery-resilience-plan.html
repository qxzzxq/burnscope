BurnScope mDNS Discovery Resilience Plan

Prepared 2026-05-27. Scope: client-side discovery, paired-device cache lifecycle, Codex daemon health/push loops, Claude statusline push child, and related tests. The core recovery fix is client-side. A small firmware /health identity field is recommended to close the duplicate-host ambiguity when mDNS is unavailable.

Summary

The client currently treats repeated transport or health failures as a reason to remove a device from paired-devices.<agent>.json. That makes sense for authorization failures, but not for reachability failures. A device can be powered off, rebooting, roaming, blocked by mDNS, or moved to a new DHCP address while it is still legitimately paired to this laptop.

The fix is to make paired-devices a durable ownership cache. Only explicit user action or an agent-specific /summary HTTP 401 should remove a pairing. Transport and health failures should mark the device unhealthy, refresh its host through mDNS by stable device_id, and keep retrying over time.

The implementation must also be race-safe: host refresh is an update-only operation, not an add operation. A stale mDNS reconciliation task must not re-insert a device that another process already removed after an agent-specific auth failure or pair-reset.

One more invariant is required: a cached host must not be trusted as proof that the intended device_id was reached. If two local device records point at the same ip:port, HTTP can succeed against one physical ESP32 while the client records success for both logical devices. Duplicate cached hosts must therefore trigger identity reconciliation even when there is no transport failure.

Current Logical Bugs

Bug Observed Behavior Root Cause Expected Behavior
Single unreachable device is permanently lost in a multi-device fleet After MAX_TRANSPORT_FAILURES, the failed device is removed. If another paired device remains, auto-pair discovery never runs because the paired list is not empty. Reachability failure is conflated with ownership loss. Keep the device paired, show it unhealthy, and recover automatically when mDNS or HTTP reachability returns.
Changed reserved/DHCP IP is not always refreshed Push-side refresh can heal stale IPs only when a push is attempted and fails. Codex can skip pushes due to semantic dedupe, so health probes keep using the stale host. Worse, if two cached device records point to the same host, HTTP can succeed against the wrong physical device and no failure path runs. Host refresh is tied only to push transport failures, not to health failures, duplicate-host detection, or periodic identity reconciliation. Reachability failures and duplicate cached hosts should trigger throttled reconciliation by device_id. HTTP success to a duplicated host should not mark every logical device healthy unless identity is verified.
Health loop can evict a device without trying mDNS recovery Codex health failures increment an in-memory counter and remove the device after five misses. The health loop calls fetch_health(cached_host) only; it does not reconcile the cached host with current mDNS data. On health failure, run one shared, throttled mDNS refresh for failed devices, retry health at the refreshed host if changed, then record failure only if still unreachable.
Manual burnscope pair is required to recover some valid pairings A device that was removed from the local cache but remains TOFU-bound on firmware can be recovered only when the entire list is empty or when the user runs pair. Normal steady-state discovery is disabled for non-empty paired lists. Normal operation should preserve pairings so recovery does not depend on re-pairing. Optional periodic reconciliation can merge already-known devices by device_id.
Failure counters are treated as eviction timers Five consecutive transport misses delete the device and its per-device status file. The counter is used for cleanup instead of status/backoff. Counters should drive health state, logging, and retry cadence, not pairing deletion.
mDNS browser ignores update events discover_all() handles only ServiceStateChange.Added. Initial browse usually works, but changed records during a browse can arrive as updates. Resolve both Added and Updated; ignore only Removed.
Stale reconciliation can resurrect removed pairings A host refresh that started from an old paired-device snapshot can call add_paired_device() after another process removed the same device. Host refresh uses an insert-or-update primitive instead of re-checking current pairing state under the paired-device lock. Use an update-only cache operation that returns false when the device is no longer paired.
Unthrottled mDNS refresh can pile up for offline devices After non-auth eviction is removed, a powered-off device can trigger a full mDNS browse on every failed push or health probe. Reconciliation is tied directly to each failure event and has no per-device cooldown. Throttle reconciliation per agent/device_id; failures inside the cooldown should update status without starting another browse.
Duplicate cached hosts can hide stale records Two paired-device entries can both point at the same ip:port. Pushing or probing both entries hits one physical device twice and can produce two apparent successes. The local cache has no uniqueness check for active host values, and current HTTP responses do not include the responding device's stable device_id. Treat duplicate hosts as an identity conflict. Reconcile the affected device_ids through mDNS, and add a firmware /health.device_id field so HTTP success can be tied to the expected device.

Target Protocol

Identity Model

  • device_id is the stable device identity, derived from the mDNS hostname seeded by the ESP32 WiFi MAC.
  • host is volatile routing data: ip:port. It must be refreshable and must never be used as proof of identity.
  • A host should normally map to at most one paired device_id for a given agent. Duplicate cached hosts are an identity conflict, not a healthy state.
  • client_id plus firmware NVS pairing slot is the authorization binding.
  • HTTP 401 from /summary for the current agent means ownership/auth mismatch and may remove the local pairing for that agent.
  • HTTP 401 from generic /health is not currently an agent-specific ownership signal. Treat it as an unhealthy probe result unless firmware changes /health to report agent-specific rejection.
  • Timeout, connect error, DNS failure, HTTP 5xx, invalid health body, mDNS absence, and duplicate-host ambiguity mean reachability, identity, or firmware health trouble. They must not remove pairing.

State Machine

paired + healthy
  on push/health success:
    keep paired, reset relevant failure counter

paired + stale_host
  on transport/health failure:
    if reconciliation cooldown allows it, discover all BurnScope devices
    if same device_id found at a different host:
      update paired-devices host only if still paired under lock
      if update succeeded, retry request once
    if retry succeeds:
      become healthy
    else:
      become paired + unhealthy

paired + host_conflict
  when multiple paired records share the same host:
    do not treat HTTP success to that host as proof for every device_id
    if reconciliation cooldown allows it, discover all BurnScope devices
    update each visible conflicted device_id to its discovered host under lock
    if all duplicates were split to distinct hosts:
      become healthy on next successful HTTP exchange
    if conflict remains unresolved:
      keep pairings, mark affected devices identity-unverified/unhealthy
      stay in host_conflict until the next cooldown-eligible reconciliation

paired + unhealthy
  on repeated transport/health failure:
    keep paired
    update per-device status with failure count and last error time
    optionally slow retry cadence
  on mDNS or HTTP success:
    update host if needed
    become healthy

paired + auth_rejected
  on HTTP 401 from /summary for this agent:
    remove only that agent/device pairing
    clear per-device push state

unpaired / forgotten
  only entered by pair-reset, manual unpair, invalid local cache, or /summary 401

Discovery Rules

  1. Run unfiltered mDNS discovery when reconciling already-paired devices. The firmware TXT paired_* flags are hints for first-time claiming, not for refreshing a known pairing.
  2. Match discovered records to cached pairings only by device_id.
  3. If a cached device_id is visible with a different host, update the local cache only through an update-only operation that re-checks the current paired list under lock.
  4. If two or more cached device_ids share the same host, force a throttled reconciliation for that duplicate-host group even if the last HTTP request succeeded.
  5. If duplicate-host reconciliation cannot prove which device responded, keep all pairings but mark the affected devices as identity-unverified rather than healthy.
  6. If a cached device_id is absent from mDNS, leave the cached host and paired state intact.
  7. Resolve both mDNS Added and Updated events.
  8. Do not add arbitrary newly-discovered devices during background reconciliation; adding new pairings remains the job of auto-pair on first run or burnscope pair.
  9. Throttle mDNS reconciliation per agent/device_id with a 60 s cooldown (override via BURNSCOPE_MDNS_RECONCILE_COOLDOWN_S). A failed request inside the cooldown should record failure state without launching another browse.

Removal Rules

HTTP 401 from /summary for this agent Yes The device is reachable and explicitly says this client is not authorized for that agent slot.
HTTP 401 from generic /health No Current firmware authorizes /health against any populated slot, not the specific agent being probed.

Implementation Plan

1. Add an Update-Only Host Cache Operation

Add a locked cache primitive in client/src/burnscope_client/host_cache.py that changes the host for an already-paired device without ever inserting a missing device. Today the only mutating primitive there is add_paired_device (insert-or-update); we deliberately want a narrower update-only sibling:

update_paired_device_host(agent, device_id, host) -> bool
  with paired-devices lock:
    current = load_paired_devices(agent)
    if device_id is not present:
      return false
    replace only that device's host
    save_paired_devices(agent, current)
    return true

This operation prevents stale reconciliation from resurrecting a pairing removed by a concurrent /summary 401 path or pair-reset.

2. Reuse and Harden the Push Refresh Helper

Keep the existing push-side shape: attempt the cached host first, then use mDNS only for devices that reported kind="transport". The helper already exists as refresh_and_retry_transport_failures in client/src/burnscope_client/pusher.py; harden it with update-only host writes and throttling:

refresh_and_retry_transport_failures(agent, paired_devices, results, timeout)
  failed = devices with kind == "transport"
  eligible = failed devices whose reconciliation cooldown has expired
  if eligible is empty:
    return original results
  discovered = discover_all(timeout=timeout)
  for each discovered device whose device_id is in eligible:
    if discovered.host != cached.host:
      if update_paired_device_host(agent, device_id, discovered.host) is false:
        skip retry because device is no longer paired
      else:
        retry push once at discovered.host
  return updated results

The throttle should be keyed by agent/device_id. For Claude statusline children it should be file-backed because each push runs in a short-lived process. For the Codex daemon it can reuse the same file-backed state or mirror it in memory with conservative persistence for consistency.

3. Detect and Reconcile Duplicate Cached Hosts

Before declaring per-device success, scan the current paired list for duplicate host values. Duplicate hosts mean at least one local record may be stale, and success from that host cannot identify which physical display accepted the request.

reconcile_duplicate_hosts(agent, paired_devices, timeout)
  duplicate_groups = host values used by more than one device_id
  affected = device_ids in duplicate_groups whose cooldown has expired
  if affected is empty:
    mark duplicate groups identity-unverified for status
    return
  discovered = discover_all(timeout=timeout)
  for each discovered device whose device_id is in affected:
    update_paired_device_host(agent, device_id, discovered.host)
  reload paired-devices
  if duplicates remain:
    keep pairings, mark affected devices identity-unverified/unhealthy

This pass should be update-only and throttled like transport recovery. It should never add new devices and never remove pairings. If mDNS is available, it will split the two records back to their current hosts. If mDNS is unavailable, the client must preserve the pairings but avoid reporting every duplicate-host entry as healthy.

4. Add Optional HTTP Device Identity

For complete protection when mDNS is unavailable, firmware should include the responding device identity in /health. /health is the natural carrier because POST /summary currently returns 204 No Content with no body — there is no place on the push path itself to read the responding device's identity, so identity verification has to ride on a follow-up GET /health.

{
  "device_id": "burnscope-5730",
  "firmware_version": "...",
  "uptime_s": 123,
  "free_heap_b": 456,
  "agents": { ... }
}

The value must match the mDNS hostname-derived device_id. The client can then treat a successful health response whose device_id differs from the requested paired record as a stale-host/identity conflict and trigger reconciliation. Until this field exists, duplicate-host conflicts can be detected locally, but resolving them depends on mDNS visibility.

5. Update Push Failure Handling

  • Keep the existing immediate push, because the cached host is usually correct.
  • Before writing per-device success, check whether the device's cached host is duplicated in the current paired list. If so, run or honor duplicate-host reconciliation and do not mark every duplicate entry healthy from the same HTTP response.
  • For devices with kind="transport", let the existing refresh-and-retry helper run one mDNS reconciliation pass only when the per-device cooldown allows it.
  • If the failed device appears at a different host, retry the push once at the refreshed host.
  • If it does not appear, appears at the same host, is inside cooldown, or was removed while discovery was in flight, keep the failure result and leave current pairing state unchanged.
  • On success, reset that device's push failure counter.
  • On continued failure, increment the counter and write per-device status, but do not evict.
  • Keep /summary 401 eviction unchanged and limited to the affected agent/device_id.

6. Update Claude Statusline Policy

  • Remove the MAX_TRANSPORT_FAILURES eviction path for transport failures (client/src/burnscope_client/claude_statusline.py; currently evicts at the fifth consecutive miss via remove_paired_device).
  • Continue persisting consecutive_failures via bump_push_failures / reset_push_failures in host_cache.py so burnscope status can show degraded devices across short-lived statusline child processes.
  • Keep /summary 401 eviction unchanged.
  • Use file-backed reconciliation throttling so frequent statusline fires do not overlap repeated mDNS browse windows for the same offline device.
  • Use the same file-backed throttling for duplicate-host reconciliation; frequent statusline fires should not repeatedly browse mDNS for an unresolved identity conflict.
  • Return non-zero from --push when any still-paired device fails, so the aggregate indicator remains honest.

7. Update Codex Push Policy

  • Remove transport-based deletion from _push_to_devices (client/src/burnscope_client/codex_daemon.py; currently evicts at MAX_TRANSPORT_FAILURES = 5).
  • Run duplicate-host reconciliation before accepting a fan-out result as fully healthy. A duplicate-host group that cannot be resolved should keep aggregate status false.
  • Keep per-device failure counters in memory for logging/status, but treat them as diagnostics rather than eviction thresholds.
  • Persist the reconciliation throttle state to a file (e.g. ~/.burnscope/mdns-reconcile.codex.json) so a daemon restart does not immediately launch a fresh browse for every offline device. Counter state can remain in memory — only the per-device_id cooldown timestamps need to survive a restart.
  • Keep /summary 401 deletion unchanged.
  • Continue advancing _last_pushed_snapshot on partial success so healthy peers are not pushed repeatedly for unchanged data.

8. Update Codex Health Policy

  • Detect duplicate cached hosts during health polling. If two records point to the same host, reconcile by mDNS before treating repeated /health successes as proof that both physical devices are healthy.
  • On health failure, collect failed devices and run one shared, throttled mDNS reconciliation pass for the batch. Share the file-backed throttle from §7 so push and health failures cannot double-trigger a browse for the same device_id within the cooldown.
  • When firmware exposes /health.device_id, compare it to the expected paired device_id. A mismatch is a stale-host/identity conflict, not a success.
  • If a failed device is discovered at a new host, retry /health once at the refreshed host.
  • If the retry succeeds, clear the health counter and use the refreshed host for future probes.
  • If the retry fails or no mDNS record is found, mark the device unhealthy and keep it paired.
  • Treat generic /health 401 as an unhealthy probe result, not as permission to remove an agent pairing.
  • Do not remove devices after five health misses (today's codex_daemon.py evicts on the fifth miss).

9. Update mDNS Resolver Events

  • Change discovery to resolve ServiceStateChange.Added and ServiceStateChange.Updated. Today client/src/burnscope_client/discovery.py short-circuits on anything other than Added.
  • Keep ignoring Removed; removal events should not delete pairings.
  • Continue deriving device_id from info.server, not the instance name.

10. Status Output Improvements

Optional but recommended: make burnscope status distinguish paired-but-unreachable from unpaired. Suggested fields:

  • paired: the device is still owned locally.
  • last_ok: timestamp of last success.
  • last_failure: timestamp and count of consecutive failures.
  • host: cached host, updated by mDNS reconciliation.
  • identity: verified, unverified, or conflict when duplicate cached hosts prevent per-device proof.
  • visible_mdns: optional, only if status chooses to perform a fresh browse.

11. Out of Scope but Tracked

Two follow-ups that share the same identity model and locking story but are explicitly out of scope for this pass:

  • OTA path. POST /ota uses the same X-BurnScope-Client-Id slot match as /summary and trusts the cached host. A duplicate-host scenario could therefore flash the wrong device. Once the client carries a verified device_id from /health, the same identity check should run before any /ota dispatch.
  • Agent-specific /health auth. Today the firmware authorises /health against any populated slot (firmware/main/http_server.c). A future firmware change should let the client specify which agent it is probing (query parameter or path), and have the firmware return 401 only when the client-id does not match that agent's slot. Until then, generic /health 401 stays an unhealthy-probe signal, not an ownership signal.

Integration Scenarios

  1. Pair two ESP32 devices. Power one off. Confirm the other keeps receiving updates and the powered-off device remains in paired-devices after more than five failed cycles.
  2. Power the device back on. Confirm mDNS sees the same device_id, host is refreshed if needed, and pushes resume without running burnscope pair.
  3. Change a device's DHCP reservation or force a new lease. Confirm the next push or health failure refreshes the cached host and recovers automatically.
  4. Manually edit two paired-device entries to point at the same ip:port. Confirm the client runs duplicate-host reconciliation even if HTTP succeeds, updates records when mDNS can see both devices, and reports unresolved entries as identity conflicts when it cannot.
  5. With firmware exposing /health.device_id, point one device record at another device's IP. Confirm the health probe detects the mismatch and does not mark the stale record healthy.
  6. Factory-reset one paired device or bind it to another client. Confirm /summary HTTP 401 removes only that device and only for the affected agent.
  7. Force a health auth failure without an agent-specific /summary rejection. Confirm the device is marked unhealthy but remains paired.
  8. Block mDNS but leave HTTP reachable at cached IP. Confirm normal pushes/health still work and absence from mDNS does not remove pairing.
  9. Block HTTP but leave mDNS visible. Confirm host refresh may update the cache, but pairing remains until HTTP recovers or /summary 401 is observed.
  10. Leave one paired device powered off and trigger frequent Claude statusline pushes. Confirm mDNS browse attempts are throttled rather than launched for every failure.

Rollout Notes

Compatibility: This plan is backwards-compatible with the current firmware TXT records. The client still uses paired_claude and paired_codex for first-time claiming decisions, but paired-device reconciliation ignores those hints and trusts local pairing plus agent-specific /summary auth.

Firmware identity field: Adding /health.device_id is backwards-compatible. Older firmware simply lacks the field; the client should then fall back to mDNS reconciliation and mark duplicate-host cases identity-unverified when it cannot prove which device responded.

Risk: The main behavior change is that unreachable devices remain visible in local status instead of being deleted. That is intentional. It may require clearer status wording so users understand the difference between “paired but offline” and “unpaired.”

Optional firmware follow-up: Add TXT fields such as boot_id or pair_epoch_<agent> later if we want richer diagnostics. (The firmware already advertises a version TXT field, so a separate fw field would be redundant.) The key identity field for duplicate-host correctness belongs in /health, where the client can validate the HTTP peer it actually reached.
